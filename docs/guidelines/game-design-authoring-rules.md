# 게임 기획서 작성 규칙과 공통 용어

> 버전: 1.0
>
> 용도: 신규 게임 착수 전에 기획자에게 전달하는 기획 문서 저작 기준
>
> 참고 배경: MineHero의 기능 설계, 밸런스 데이터, 진행·해금, 저장, 현지화 운영 방식에서 재사용 가능한 원칙을 추려 일반화했다.
>
> 적용 범위: 게임 개요서, 시스템 기획서, 콘텐츠 기획서, 밸런스 표, UI 흐름, 라이브 운영 기획

---

## 이 문서의 목적

좋은 기획서는 아이디어를 멋지게 설명하는 문서에 그치지 않는다. 기획, 개발, 아트, QA가 같은 게임을 상상하고 아래 질문에 같은 답을 낼 수 있어야 한다.

- 플레이어가 왜 이 기능을 사용하는가?
- 언제 시작되고, 어떤 조건에서 허용되며, 무엇이 변하는가?
- 정상 상황과 예외 상황에서 각각 어떻게 동작하는가?
- 어떤 수치와 문구를 데이터로 관리하는가?
- 종료하거나 다시 접속했을 때 무엇이 남는가?
- 무엇을 확인하면 구현 완료라고 판단할 수 있는가?

모든 기능은 가능하면 아래 순서로 설명한다.

> **플레이어 가치 → 플레이 흐름 → 규칙 → 상태 변화 → 데이터 → 화면 피드백 → 수락 기준**

이 순서가 뒤집혀 수치표나 화면 목록부터 나오면, 구현은 가능해도 왜 필요한 기능인지 판단하기 어려워진다.

## 가장 먼저 지켜야 할 원칙

### 플레이어 경험과 구현 명세를 분리한다

- 기획서는 먼저 플레이어가 무엇을 보고, 선택하고, 느끼는지를 설명한다.
- 그다음 그 경험을 만드는 규칙, 상태, 데이터, 예외를 명세한다.
- 특정 엔진의 클래스명이나 파일 구조는 게임 규칙이 아니다. 기술 제약이 확정된 경우에만 별도 제약으로 기록한다.
- “재미있게”, “적당히”, “자연스럽게”, “확률적으로”처럼 사람마다 다르게 해석할 표현은 단독 규칙으로 쓰지 않는다.

나쁜 예:

> 보스가 가끔 강한 공격을 하고 플레이어가 잘 피하도록 한다.

좋은 예:

> 보스 체력이 50% 이하가 되면 전방 부채꼴 공격을 사용 후보에 추가한다. 공격 0.8초 전에 위험 영역을 표시하며, 피격 시 최대 체력의 30% 피해와 1초 넉백을 적용한다. 같은 공격은 연속으로 선택되지 않는다.

### 한 정보에는 하나의 원본만 둔다

같은 규칙이나 수치를 여러 문서에 복사하지 않는다. 중복된 정보는 언젠가 서로 달라진다.

- 게임의 큰 방향은 상위 기획서가 소유한다.
- 기능의 상세 규칙은 해당 기능 기획서가 소유한다.
- 반복되는 수치는 밸런스 표가 소유한다.
- 반복되는 이름과 번역은 용어집과 현지화 표가 소유한다.
- 다른 문서에서는 내용을 다시 쓰지 말고 원본 위치를 링크한다.
- 규칙이 바뀌면 원본과 그 규칙을 검증하는 수락 기준을 함께 갱신한다.

### 확정, 가정, 미정을 섞지 않는다

문서 상단에 상태를 표시하고, 미확정 사항은 본문에 확정 문장처럼 쓰지 않는다.

| 상태 | 의미 |
| --- | --- |
| 초안 | 방향과 범위를 검토하는 중이다. 구현 기준으로 사용하지 않는다. |
| 검토 중 | 주요 규칙은 있으나 열린 결정이 남아 있다. |
| 확정 | 담당자가 구현 기준으로 사용할 수 있다. |
| 구현 중 | 확정 명세를 기준으로 제작 중이다. 변경 시 영향 확인이 필요하다. |
| 검증 중 | 구현은 끝났으며 수락 기준과 실제 플레이를 확인 중이다. |
| 완료 | 수락 기준을 통과했고 남은 필수 결정이 없다. |
| 보류 | 재개 조건이 충족될 때까지 작업하지 않는다. |
| 폐기 | 더 이상 유효하지 않다. 대체 문서나 폐기 이유를 기록한다. |

결정되지 않은 내용은 반드시 다음 중 하나로 표시한다.

- **가정**: 당장 진행하기 위해 임시로 채택한 전제
- **열린 결정**: 담당자의 선택이 필요한 항목
- **검증 필요**: 플레이테스트나 데이터로 확인해야 하는 항목
- **후속 범위**: 이번에는 만들지 않지만 연결 지점을 보존할 항목

### 기능 이름으로 소통한다

- 문서 내부 추적용 번호는 사용할 수 있지만, 제목과 보고에는 기능 이름을 함께 쓴다.
- “두 번째 작업”, “기능 A”, “버튼 3”만으로 대상을 부르지 않는다.
- 사용자에게 보이는 이름, 기획 용어, 내부 식별자는 구분한다.

예:

| 구분 | 예시 |
| --- | --- |
| 사용자 표시명 | 강화 |
| 기획 용어 | 장비 옵션 강화 |
| 내부 식별자 | `EQUIPMENT_OPTION_ENHANCE` |

### 규칙은 조건과 결과가 보이게 쓴다

규칙 한 줄에는 가능하면 다음 요소를 포함한다.

> **주체 + 트리거 + 선행 조건 + 행동 또는 결과 + 실패 시 결과**

예:

> 플레이어가 제작 버튼을 누르면, 재료와 제작 슬롯이 모두 충분한 경우 재료를 차감하고 결과물을 지급한다. 하나라도 부족하면 아무 값도 바꾸지 않고 부족한 항목을 안내한다.

“차감 후 지급 실패”처럼 중간 상태가 가능한 기능은 원자성 또는 복구 규칙도 적는다.

## 기획 문서의 권장 구조

프로젝트 전체를 한 문서에 무한히 쌓지 않는다. 문서의 높이를 다음처럼 나눈다.

| 문서 | 소유하는 내용 | 포함하지 않을 내용 |
| --- | --- | --- |
| 게임 개요서 | 비전, 타깃, 핵심 재미, 핵심 루프, 성장 구조, 콘텐츠 지도, 사업·플랫폼 제약 | 개별 버튼 좌표, 몬스터별 세부 수치 |
| 기능 기획서 | 한 기능의 목적, 범위, 흐름, 규칙, 상태, 데이터, 예외, 수락 기준 | 다른 기능의 상세 규칙 복제 |
| 콘텐츠 명세 | 몬스터, 아이템, 스테이지, 퀘스트 등 반복 콘텐츠의 정의와 차별점 | 공통 시스템 규칙 복제 |
| 밸런스 표 | 반복 수치, 식별자, 참조 관계, 확률, 비용, 보상 | 장문의 의도 설명, 화면 흐름 |
| 용어집 | 공식 표기, 정의, 금지 동의어, 번역 | 기능별 상세 동작 |
| 결정 기록 | 바뀐 결정, 날짜, 이유, 영향 범위 | 현재 규칙의 중복 설명 |

작은 프로젝트는 파일을 합칠 수 있다. 다만 한 정보의 원본이 어디인지는 항상 분명해야 한다.

## 게임 개요서에 반드시 들어갈 내용

### 한 줄 설명

장르명만 쓰지 말고 플레이어 행동과 차별점을 함께 쓴다.

> `[대상 플레이어]가 [핵심 행동]을 반복하며 [독특한 변화 또는 목표]를 경험하는 [장르] 게임`

예:

> 짧은 세션을 선호하는 플레이어가 광산을 탐험하고 자원을 가져와 장비를 성장시키며, 매번 달라지는 지하 환경을 공략하는 캐주얼 액션 RPG.

### 제품 목표와 성공 지표

- 게임이 해결하려는 플레이어 욕구
- 목표 플랫폼과 입력 방식
- 예상 플레이 세션 길이
- 목표 플레이 기간 또는 콘텐츠 수명
- 핵심 사업 목표가 있다면 해당 지표와 기능의 연결
- 출시 범위와 출시 후 범위

지표를 쓸 때는 “리텐션 개선”으로 끝내지 말고 어떤 행동을 통해 개선할지 가설을 쓴다.

> 일일 미션이 다음 접속 목적을 제공하여 첫 주 재방문을 높인다. 검증 지표는 미션 노출률, 수락률, 완료율, 보상 수령률, 미션 참여자의 다음 날 재방문율이다.

### 디자인 기둥

게임의 주요 의사결정을 걸러내는 원칙을 3~5개로 제한한다. 서로 겹치지 않아야 한다.

예:

- 짧은 시간에도 눈에 보이는 성장이 있다.
- 위험을 감수할수록 귀환 보상이 커진다.
- 실패해도 다음 도전을 위한 정보나 자산을 얻는다.

새 기능은 어떤 디자인 기둥에 기여하는지 적는다. 어디에도 기여하지 않는 기능은 우선순위를 다시 검토한다.

### 핵심 루프와 메타 루프

- **순간 루프**: 수 초 단위의 입력과 피드백
- **세션 루프**: 한 번 접속해 시작하고 종료할 때까지의 반복
- **메타 루프**: 여러 세션에 걸친 성장, 수집, 해금
- **장기 루프**: 콘텐츠 완주, 시즌, 빌드 완성 등 장기 목표

각 루프는 `행동 → 즉시 피드백 → 보상 → 다음 선택`이 이어져야 한다. 보상을 받아도 다음 선택이 생기지 않으면 루프가 끊긴다.

### 콘텐츠와 시스템 지도

콘텐츠와 시스템을 구분하고 의존 관계를 표시한다.

- 시스템: 반복 콘텐츠가 따라야 하는 공통 규칙. 예: 전투, 인벤토리, 퀘스트, 제작.
- 콘텐츠: 시스템에 들어가는 개별 항목. 예: 특정 검, 특정 몬스터, 특정 퀘스트.

“몬스터 30종”은 콘텐츠 규모이고, “경고 후 공격하고 상태 이상을 적용하는 전투 규칙”은 시스템 명세다.

## 기능 기획서에 반드시 들어갈 내용

### 목적과 플레이어 가치

- 현재 어떤 문제가 있는가?
- 플레이어에게 어떤 새로운 선택, 감정, 목표를 주는가?
- 게임의 어느 루프와 디자인 기둥에 기여하는가?
- 성공하면 플레이 행동이 어떻게 바뀌는가?

### 범위와 비범위

이번 작업에 포함되는 것과 포함되지 않는 것을 모두 쓴다.

- **포함**: 이번에 실제로 완성해야 하는 사용자 경험과 규칙
- **비범위**: 유사해 보이지만 이번에는 만들지 않는 것
- **후속 연결점**: 나중에 확장할 가능성이 있어 지금 보존해야 할 상태나 데이터

비범위는 “나중에”라는 말만 쓰지 말고, 재논의 조건이 있다면 함께 적는다.

### 진입, 진행, 종료 흐름

최소한 다음 흐름을 순서대로 적는다.

1. 플레이어가 기능을 발견하거나 진입하는 방법
2. 기능이 열리는 조건과 닫히는 조건
3. 플레이어가 내리는 선택
4. 비용 확인과 소비 시점
5. 결과 계산과 보상 지급 시점
6. 성공, 실패, 취소 시 피드백
7. 기능을 종료한 뒤 남는 변화

필요하면 상태 전이 표를 사용한다.

| 현재 상태 | 트리거 | 조건 | 다음 상태 | 상태 변화와 피드백 |
| --- | --- | --- | --- | --- |
| 잠김 | 화면 진입 | 해금 조건 미충족 | 잠김 | 잠금 이유와 다음 목표 표시 |
| 사용 가능 | 실행 선택 | 비용 충분 | 처리 중 | 중복 입력 차단, 비용 예약 |
| 처리 중 | 결과 확정 | 성공 | 완료 | 비용 확정, 보상 지급, 결과 연출 |
| 처리 중 | 결과 확정 | 실패 | 사용 가능 | 실패 규칙에 따라 비용 처리, 실패 이유 표시 |

### 상세 규칙

규칙은 우선순위가 높은 것부터 번호를 매겨 쓴다. 다음 내용을 빠뜨리지 않는다.

- 동일 시점에 규칙이 충돌하면 무엇이 우선하는가?
- 상한과 하한은 포함인가, 미포함인가?
- 여러 보너스는 합연산인가, 곱연산인가, 순차 적용인가?
- 비용은 시도 시점, 성공 시점, 수령 시점 중 언제 차감되는가?
- 보상은 즉시 지급인가, 수령 버튼이 필요한가?
- 중복 실행, 연타, 네트워크 지연, 강제 종료 시 결과는 무엇인가?
- 조건이 진행 도중 사라지면 계속하는가, 중단하는가?
- 같은 결과를 여러 경로에서 받을 수 있다면 중복 지급을 어떻게 막는가?

### UI와 피드백

화면의 모양보다 정보 우선순위와 상태별 반응을 먼저 정의한다.

- 화면 진입 시 가장 먼저 알아야 할 정보
- 선택 가능한 것과 선택 불가능한 것의 구분
- 비용, 보상, 성공 확률, 남은 시간의 표시 위치와 형식
- 성공, 실패, 잠김, 재료 부족, 최대치 도달 피드백
- 팝업을 닫거나 뒤로 갔을 때의 처리
- 입력 장치, 화면 크기, 접근성 고려
- 진동, 소리, 카메라, 이펙트가 전달해야 하는 의미

레이아웃 수치는 와이어프레임이 소유하고, 기능 기획서는 “무엇이 보여야 하는가”와 “상태에 따라 어떻게 바뀌는가”를 소유한다.

### 데이터와 밸런스

- 어떤 항목이 반복 데이터인가?
- 각 항목의 고유 식별자는 무엇인가?
- 기획자가 코드 수정 없이 조정해야 할 값은 무엇인가?
- 값의 단위와 허용 범위는 무엇인가?
- 다른 표의 어떤 식별자를 참조하는가?
- 누락되면 오류인가, 의도적인 빈값인가?
- 전체 밸런스에 영향을 주는 공식은 무엇인가?

### 저장과 초기화

각 상태를 다음 중 하나로 분류한다.

| 분류 | 설명 | 예시 |
| --- | --- | --- |
| 영구 저장 | 앱 종료, 사망, 스테이지 이동 후에도 유지 | 계정 레벨, 영구 해금 |
| 세션 저장 | 현재 접속 또는 현재 런 동안만 유지 | 세션 누적 보너스 |
| 스테이지 저장 | 현재 스테이지를 나갔다 돌아오면 복원 | 열린 문, 채집 완료 오브젝트 |
| 일시 상태 | 종료나 재진입 시 사라짐 | 투사체, 순간 경직 |
| 파생 상태 | 원본 값으로 다시 계산하며 직접 저장하지 않음 | 전투력 합계, 표시용 진행률 |

반드시 다음 상황을 결정한다.

- 정상 종료와 강제 종료
- 사망과 부활
- 스테이지 이동과 귀환
- 새 게임 또는 계정 초기화
- 구버전 저장 데이터의 복원
- 보상 지급 도중 종료

“저장한다”만 적지 말고 저장 시점과 허용 가능한 손실 범위를 적는다.

### 분석 이벤트

분석이 필요한 기능은 화면 노출만 기록하지 않는다. 퍼널을 재구성할 수 있게 최소 이벤트를 정의한다.

- 노출
- 진입 또는 선택
- 비용 확인
- 실행
- 성공 또는 실패
- 보상 수령
- 취소 또는 이탈

이벤트에는 가능한 한 기능 식별자, 콘텐츠 식별자, 전후 잔액, 결과, 실패 이유를 포함한다. 개인정보나 자유 입력 텍스트는 불필요하게 수집하지 않는다.

### 수락 기준

수락 기준은 구현 방법이 아니라 관찰 가능한 결과로 쓴다.

권장 형식:

> **Given** 사전 상태 / **When** 플레이어 행동 / **Then** 관찰 결과

예:

> Given 플레이어가 철 광석 5개를 보유하고 제작 슬롯이 비어 있을 때, When 철검 제작을 선택하면, Then 광석 5개가 차감되고 철검 1개가 지급되며 제작 완료 피드백이 한 번만 재생된다.

최소한 아래 사례를 포함한다.

- 정상 성공
- 선행 조건 미충족
- 경계값과 최대치
- 취소 또는 뒤로 가기
- 중복 입력
- 저장 후 재접속
- 실패 또는 복구 경로
- 다른 기능과 맞닿는 대표 사례

## 상태, 조건, 해금을 쓰는 규칙

### 트리거와 자격 조건을 구분한다

- **트리거**: 지금 기능을 실행하거나 보여줄 상황인가?
- **자격 조건**: 이 플레이어가 그 기능을 사용할 수 있는가?

예:

- 내구도가 0이 됨: 수리 제안의 트리거
- 튜토리얼 퀘스트 완료: 수리 제안을 볼 수 있는 자격 조건

최종 실행 조건은 보통 `트리거 충족 AND 자격 조건 충족`이다. 둘을 섞으면 왜 기능이 보이지 않는지 추적하기 어렵다.

### 해금, 노출, 활성, 완료를 구분한다

| 용어 | 의미 |
| --- | --- |
| 해금 | 이후 사용할 자격을 영구 또는 장기적으로 얻음 |
| 노출 | 화면에 보이거나 발견 가능해짐 |
| 활성 | 지금 상호작용하거나 효과를 받을 수 있음 |
| 진행 중 | 시작했으나 완료되지 않음 |
| 완료 | 목표 조건을 충족함 |
| 수령 완료 | 완료 보상을 실제로 받음 |

완료와 보상 수령은 같은 상태일 수도, 다른 상태일 수도 있다. 다른 상태라면 저장과 중복 지급 규칙을 반드시 명시한다.

### 조건식은 논리를 명시한다

- 조건이 둘 이상이면 AND인지 OR인지 반드시 쓴다.
- 중첩 조건은 괄호나 조건 트리로 표현한다.
- “레벨 10 또는 퀘스트 완료 후 보유 골드 100 이상”은 다음처럼 모호하다.
- 올바른 예: `(레벨 10 이상 OR 퀘스트 완료) AND 보유 골드 100 이상`.
- 존재하지 않는 조건이나 잘못된 참조가 들어왔을 때 열리는지 닫히는지도 정한다. 보상, 결제, 광고, 고가치 콘텐츠는 기본적으로 닫히는 쪽이 안전하다.

## 경제와 보상을 쓰는 규칙

### 재화, 아이템, 점수를 구분한다

- **재화**: 잔액으로 보유하고 비용으로 반복 소비하는 가치. 예: 골드, 젬.
- **아이템**: 개별 종류와 수량 또는 인스턴스를 가진 소유물. 예: 광석, 검.
- **점수**: 순위나 목표 진행을 나타내며 보통 직접 소비하지 않는 값.
- **경험치**: 성장 임계치를 향한 누적 진행 값.
- **티켓**: 입장 횟수나 시도를 제한하는 소비 자원.

하나의 값이 여러 역할을 맡으면 획득, 소비, 저장, UI 규칙이 충돌하기 쉬우므로 역할을 분명히 한다.

### 모든 획득과 소비에는 출처와 이유가 있다

- 보상에는 `어디서, 왜, 무엇을, 얼마나` 지급하는지 쓴다.
- 비용에는 `어디서, 왜, 무엇을, 얼마나` 소비하는지 쓴다.
- 고가치 재화는 가능하면 잔액 변화 이력을 추적할 수 있어야 한다.
- 지급과 소비를 여러 화면에서 제각각 구현하지 않도록 공통 규칙을 둔다.

### 소스와 싱크를 함께 본다

- **소스**: 재화나 아이템이 게임 안으로 들어오는 경로
- **싱크**: 재화나 아이템이 게임에서 빠져나가는 경로

새 소스를 추가할 때는 해당 자원의 싱크와 보유 상한을 확인한다. 새 싱크를 추가할 때는 무과금·초보 플레이어도 필요한 양을 얻을 수 있는지 확인한다.

### 중복 지급과 부분 실패를 막는다

보상 지급, 비용 차감, 상태 완료가 함께 일어나야 한다면 한 덩어리로 성공하거나 복구할 수 있어야 한다.

반드시 결정할 질문:

- 비용은 빠졌지만 보상이 지급되지 않으면 어떻게 복구하는가?
- 보상은 지급됐지만 완료 표시가 저장되지 않으면 다시 받을 수 있는가?
- 광고나 결제 콜백이 두 번 오면 중복 지급되는가?
- 인벤토리가 가득 찼다면 지급을 막는가, 우편으로 보내는가, 바닥에 떨어뜨리는가?

## 수치, 공식, 확률, 시간을 쓰는 규칙

### 모든 수치에 단위를 붙인다

나쁜 예: `Cooldown = 5`, `Chance = 20`, `Speed = 2`

좋은 예: `CooldownSec = 5`, `DropChancePct = 20`, `MoveSpeedTilePerSec = 2`

문서와 표에 최소한 다음을 명시한다.

- 단위: 초, 밀리초, 픽셀, 타일, 퍼센트, 개수, 배수
- 값 범위: 최소, 최대, 포함 여부
- 반올림: 버림, 올림, 반올림과 적용 시점
- 표시 자릿수와 내부 계산 정밀도
- 기준값: 기본 공격력, 최대 체력, 현재 체력 중 무엇을 기준으로 하는가?

### 공식은 계산 순서를 고정한다

예:

```text
최종 피해 = max(1, round((기본 피해 + 고정 보너스) × (1 + 비율 보너스) × 치명타 배율))
```

공식 아래에 다음을 함께 적는다.

- 각 변수의 출처
- 합연산과 곱연산의 순서
- 상한과 하한
- 반올림 시점
- 같은 종류 보너스의 중첩 방식
- 예시 입력과 기대 출력 2~3개

### 확률의 표본 공간을 명시한다

- 20%는 `0.2`인지 `20`인지 표준을 정한다.
- 각 항목을 독립 추첨하는지, 가중치 목록에서 하나를 뽑는지 구분한다.
- 여러 개가 동시에 나올 수 있는지 적는다.
- 최소·최대 획득 종류와 수량을 구분한다.
- 실패 누적 보정, 천장, 중복 방지, 시드가 있다면 명시한다.
- 화면에 표시하는 확률과 실제 확률이 다르면 안 된다.

### 시간의 종류를 구분한다

| 시간 | 의미 |
| --- | --- |
| 실제 시간 | 앱을 꺼도 흐르는 달력 기준 시간 |
| 세션 시간 | 현재 접속 또는 현재 플레이 동안 누적되는 시간 |
| 게임 시간 | 일시정지, 연출, 배속의 영향을 받는 시뮬레이션 시간 |
| 쿨다운 | 특정 행동을 다시 할 수 있을 때까지의 시간 |
| 지속 시간 | 효과가 유지되는 시간 |
| 리셋 주기 | 일일, 주간, 시즌 등 상태가 초기화되는 기준 |

“24시간 후”와 “다음 날 00시”는 다른 규칙이다. 시간대, 서버 시간, 오프라인 경과, 일광 절약 시간의 영향을 받는지도 적는다.

## 밸런스 표와 식별자 작성 규칙

### 식별자는 이름이 아니라 정체다

- 사람이 보는 이름과 변하지 않는 식별자를 분리한다.
- 식별자는 가능하면 `UPPER_SNAKE_CASE`를 사용한다.
- 출시 후 저장이나 분석에 쓰인 식별자는 이름이 바뀌어도 재사용하거나 번호를 바꾸지 않는다.
- 삭제한 식별자를 다른 콘텐츠에 재활용하지 않는다.
- 화면 표시명은 현지화 키로 연결한다.

예:

| Id | NameKey | Category | Tier |
| --- | --- | --- | --- |
| `IRON_SWORD` | `ITEM_IRON_SWORD_NAME` | `WEAPON` | 3 |

### 빈값, 0, false는 서로 다른 뜻이다

- 빈값 또는 `null`: 값이 없거나 해당하지 않음
- `0`: 값이 있으며 그 값이 0임
- `false`: 명시적으로 꺼짐
- 빈 배열: 목록이 존재하지만 항목이 없음

각 컬럼에서 빈값이 허용되는지, 허용된다면 어떤 의미인지 정의한다. 누락된 필수 값에 코드가 임의 기본값을 넣어 조용히 동작하게 하지 않는다. 필수 값이 없으면 데이터 검증에서 실패해야 한다.

### 참조는 반드시 검증한다

- 레시피의 재료 식별자는 아이템 표에 존재해야 한다.
- 퀘스트의 대상 식별자는 해당 대상 표에 존재해야 한다.
- 보상의 대상 식별자는 재화 또는 아이템 카탈로그에 존재해야 한다.
- 해금 조건이 참조하는 퀘스트나 레벨은 실제 도달 가능해야 한다.
- 배열의 항목 수가 서로 짝을 이루면 길이가 같은지 검증한다.

### 표의 각 컬럼을 정의한다

| 항목 | 반드시 적을 내용 |
| --- | --- |
| 컬럼명 | 일관된 영문 식별자 |
| 타입 | string, enum, integer, number, boolean, id reference, array |
| 필수 여부 | 필수, 선택, 조건부 필수 |
| 단위 | sec, ms, pct, count, pixel, tile 등 |
| 허용 범위 | 최소·최대·enum 목록 |
| 빈값 의미 | 해당 없음, 자동 계산, 금지 중 하나 |
| 참조 대상 | 다른 표와 컬럼 |
| 설명 | 기획 의도보다 실행 규칙 중심의 짧은 정의 |

### 정렬 순서와 표시 순서를 분리한다

식별자 이름이나 표의 현재 행 순서에 표시 순서를 의존하지 않는다. 순서가 중요한 콘텐츠에는 `SortOrder`, `OrderIndex`, `Priority` 같은 명시적 값을 둔다.

## 문구와 용어 작성 규칙

### 용어집을 단일 원본으로 유지한다

반복되는 게임 용어는 처음 등장할 때 아래 형식으로 등록한다.

| 기획 용어 | 사용자 표시명 | 정의 | 사용하지 않을 표현 | 영문 표준 |
| --- | --- | --- | --- | --- |
| 장비 강화 | 강화 | 보유 장비의 기존 능력치를 단계적으로 높이는 기능 | 업글, 제련 | Enhancement |

- 같은 개념에 여러 이름을 쓰지 않는다.
- 다른 개념에 같은 이름을 쓰지 않는다.
- 내부 구현 용어를 사용자 문구에 그대로 노출하지 않는다.
- 번역할 때 반복 용어의 표기를 매번 새로 만들지 않는다.

### 사용자 문장은 한 화면 안에서 같은 말투를 쓴다

- 안내문, 토스트, 아이템 설명, 오류 문구는 프로젝트가 정한 말투를 따른다.
- 버튼과 탭은 짧은 명사구 또는 행동형으로 통일한다.
- 실패 문구는 가능하면 이유와 다음 행동을 함께 말한다.
- “오류가 발생했습니다”만 쓰지 말고 플레이어가 해결할 수 있는 경우 방법을 안내한다.

예:

- 좋음: `재료가 부족합니다. 철 광석 3개가 더 필요합니다.`
- 나쁨: `제작할 수 없습니다.`

### 현지화를 처음부터 고려한다

- 화면 문구를 이미지나 코드에 직접 박지 않는다.
- 조합 문장은 언어마다 어순이 달라질 수 있으므로 완성된 문장 키를 우선한다.
- 변수에는 의미 있는 이름을 쓴다. 예: `{currentCount}`, `{requiredCount}`.
- 버튼 폭과 줄바꿈은 번역 문자열이 길어질 가능성을 고려한다.
- 복수형, 성별, 조사, 숫자 표기, 날짜·시간 형식을 로케일별로 검토한다.

## 우선순위와 일정 작성 규칙

우선순위는 중요도와 일정 희망을 섞지 않는다. 각 단계의 정의를 프로젝트 시작 시 합의한다.

| 우선순위 | 권장 정의 |
| --- | --- |
| 필수 | 이것이 없으면 목표 경험이나 출시 조건을 충족하지 못함 |
| 중요 | 목표 품질과 성과에 크게 기여하지만 축소 대안이 있음 |
| 선택 | 여력이 있을 때 추가하며 없어도 핵심 루프가 성립함 |
| 보류 | 재논의 조건이 충족되기 전에는 착수하지 않음 |

각 기능에는 다음을 함께 적는다.

- 우선순위의 근거
- 선행 의존 기능
- 병렬 진행 가능한 작업
- 가장 큰 불확실성
- 축소 가능한 범위
- 일정이 부족할 때 버릴 순서
- 재검토 시점 또는 재개 조건

“전부 중요”는 우선순위가 없는 것과 같다. 출시 범위는 기능 추가 목록뿐 아니라 제외 목록으로도 관리한다.

## 자주 발생하는 나쁜 기획 패턴

### 화면 목록만 있고 규칙이 없다

버튼과 팝업은 기능의 표현일 뿐이다. 상태 변화, 비용 시점, 실패 처리, 저장 규칙이 없으면 기능이 정의되지 않은 것이다.

### 정상 흐름만 있다

재료 부족, 인벤토리 가득 참, 최대치, 연타, 취소, 재접속, 보상 중단 상황이 빠지면 QA와 개발이 각자 규칙을 만들어 낸다.

### 수치가 설명 없이 흩어져 있다

같은 쿨다운이 본문, 표, 와이어프레임에 각각 쓰이면 서로 다른 값이 된다. 수치는 한 표가 소유하고 문서는 의미와 공식을 설명한다.

### 비슷한 용어를 섞어 쓴다

해금, 노출, 활성, 완료, 수령을 모두 “오픈”이라고 부르면 저장 상태와 UI가 엇갈린다.

### 빈값을 임의 기본값으로 처리한다

필수 수치가 빠졌는데 게임이 그럴듯한 기본값으로 동작하면 데이터 오류를 발견하기 어렵다. 필수 값 누락은 제작 단계에서 실패하게 한다.

### 구현 세부가 플레이어 규칙을 대신한다

“컨트롤러에서 이벤트를 보낸다”는 구현 방법이지 플레이어 규칙이 아니다. 기획서는 언제 무엇이 발생하고 어떤 결과가 보이는지를 먼저 적는다.

### 확장 가능성을 이유로 현재 필요 없는 규칙을 만든다

확정되지 않은 시즌, 네트워크, 등급, 용량, 예외를 미리 설계하면 현재 기능의 핵심이 흐려진다. 지금 필요한 최소 규칙과 후속 확장 경계만 적는다.

### 검증할 수 없는 수락 기준을 쓴다

“자연스럽다”, “재미있다”, “충분히 빠르다”는 단독 수락 기준이 될 수 없다. 관찰 가능한 행동, 수치, 비교 대상, 플레이테스트 질문으로 바꾼다.

## 기획서 제출 전 체크리스트

### 방향과 범위

- [ ] 한 줄 설명만 읽어도 대상, 핵심 행동, 차별점을 알 수 있다.
- [ ] 이 기능이 해결하는 플레이어 문제와 기대 감정이 적혀 있다.
- [ ] 포함 범위와 비범위가 모두 적혀 있다.
- [ ] 게임의 핵심 루프 또는 디자인 기둥과 연결되어 있다.
- [ ] 선행 의존성과 가장 큰 불확실성이 드러난다.

### 규칙과 상태

- [ ] 진입, 진행, 성공, 실패, 취소, 종료 흐름이 있다.
- [ ] 트리거와 자격 조건이 구분되어 있다.
- [ ] 해금, 노출, 활성, 완료, 수령 상태가 구분되어 있다.
- [ ] 비용 차감 시점과 보상 지급 시점이 명확하다.
- [ ] 상한, 하한, 중복, 우선순위, 중첩 규칙이 명확하다.
- [ ] 연타, 강제 종료, 재접속, 최대치, 부족 상태가 정의되어 있다.

### 데이터와 밸런스

- [ ] 모든 수치에 단위가 있다.
- [ ] 공식의 계산 순서, 반올림, 상·하한이 정의되어 있다.
- [ ] 확률의 방식과 표본 공간이 명확하다.
- [ ] 반복 콘텐츠에 변하지 않는 식별자가 있다.
- [ ] 빈값, 0, false의 의미가 구분되어 있다.
- [ ] 다른 표를 참조하는 식별자의 무결성을 검사할 수 있다.
- [ ] 기획자가 조정해야 할 값은 데이터 원본이 정해져 있다.

### 저장, 경제, 운영

- [ ] 어떤 상태를 언제 저장하고 초기화하는지 적혀 있다.
- [ ] 허용 가능한 저장 손실 범위가 적혀 있다.
- [ ] 재화와 아이템의 소스와 싱크가 확인되어 있다.
- [ ] 중복 지급과 부분 실패를 막는 규칙이 있다.
- [ ] 기존 유저 데이터가 있다면 마이그레이션 정책이 있다.
- [ ] 출시 후 조정할 항목과 앱 업데이트가 필요한 항목이 구분되어 있다.

### UI, 문구, 검증

- [ ] 상태별로 보여야 할 정보와 피드백이 적혀 있다.
- [ ] 실패 문구가 이유와 가능한 다음 행동을 알려준다.
- [ ] 공식 용어와 문체가 일관되어 있다.
- [ ] 현지화될 문구와 변수 형식이 정의되어 있다.
- [ ] 정상, 실패, 경계, 저장 복원 사례의 수락 기준이 있다.
- [ ] 분석이 필요하다면 퍼널 이벤트와 핵심 속성이 정의되어 있다.
- [ ] 열린 결정에 담당자와 결정 필요 시점이 있다.

## MineHero에서 일반화한 핵심 교훈

- 성장축은 각각 다른 역할을 가져야 한다. 같은 보상을 여러 이름으로 반복하면 선택이 아니라 숫자 중복이 된다.
- 제작, 성장, 광고 같은 새 소스에는 재료를 지속 소비할 싱크와 경제 영향을 함께 설계해야 한다.
- 해금 조건과 지금 보여줄 상황을 분리하면 기능 노출 문제를 설명하고 테스트하기 쉬워진다.
- 저장 여부뿐 아니라 저장 소유자, 저장 시점, 강제 종료 시 손실 한도를 정해야 복사와 증발을 막을 수 있다.
- 콘텐츠 식별자와 표시명을 분리하면 이름 변경, 번역, 저장 호환, 분석이 안전해진다.
- 필수 설정값이 없을 때 그럴듯한 기본값으로 숨기지 않아야 데이터 오류를 출시 전에 발견할 수 있다.
- 게임 내 반복 용어와 문체는 기능별 취향이 아니라 프로젝트 전체 규칙으로 관리해야 한다.
- 기능 완료는 “화면이 보인다”가 아니라 정상·실패·경계·저장 복원 수락 기준을 통과한 상태다.

이 기준을 모두 채우는 것이 문서를 길게 만드는 목적은 아니다. 구현과 검증에 영향을 주지 않는 설명은 줄이고, 서로 다른 해석을 만들 수 있는 규칙과 상태는 반드시 남긴다.
