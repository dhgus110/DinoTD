# 기획 원본의 개발 인계 규칙

## 1. 목적

이 문서는 이 저장소의 기획 원본을 개발 저장소 `Dino_TD`로 옮길 때 두 저장소의 역할과 변경 순서를
정한다. 기획 담당자는 플레이어가 이해할 수 있는 규칙과 공식 용어에 집중하고, 개발 담당자는 같은
내용을 구현 단위로 나눠 추적한다.

## 2. 저장소 역할

- 이 저장소 `DinoTD`는 게임 기획과 공식 용어의 단일 원본이다.
- 개발 저장소 `Dino_TD`의 `docs/design`은 구현을 위한 파생 계약이다. 기획 원본을 대신하지 않는다.
- 이 저장소에서는 기능 ID, 규칙 ID와 수용 조건 ID를 사용하지 않는다.
- 개발 저장소로 반입할 때 개발 담당자가 `feature_id`, 규칙 ID와 수용 조건 ID를 부여한다.
- 두 저장소의 파일 구조를 억지로 같게 만들지 않는다. 개발 저장소의 원본 매핑표가 기획 문서의
  커밋, 경로와 절을 구현 기능에 연결한다.

## 3. 기획 담당자의 인계 단위

기획 변경을 전달할 때 다음 정보를 빠짐없이 남긴다.

1. 변경한 기획 문서와 절
2. 변경 상태: `확정`, `가정`, `미정`, `검증 필요`
3. 변경 이유와 플레이어 경험에 미치는 영향
4. 함께 확인한 관련 원본과 공식 용어
5. 변경이 포함된 `main` 커밋

기획 담당자는 개발 저장소의 기능 ID를 알 필요가 없다. 개발 담당자가 원본 매핑표를 보고 영향을
받는 기능을 찾는다.

## 4. 변경 방향별 순서

### 4.1 기획에서 시작한 변경

1. 이 저장소의 원본 문서와 용어집을 함께 수정한다.
2. 확인 사례와 변경 기록을 새 규칙에 맞춘다.
3. 작업 브랜치를 검증하고 `main`에 병합한다.
4. 개발 담당자에게 `main` 커밋과 변경 문서·절을 전달한다.
5. 개발 저장소에서 원본 매핑, 파생 기획 계약, 구현 계획과 코드를 같은 변경으로 갱신한다.

### 4.2 구현 또는 테스트에서 시작한 변경

1. 개발 담당자가 현재 기획 원본과 발견한 차이, 추천 변경과 영향 범위를 기획 담당자에게 전달한다.
2. 기획 규칙이 바뀌는 경우 이 저장소의 원본 문서를 먼저 수정하고 `main`에 병합한다.
3. 개발 저장소는 새 기획 원본 커밋을 참조한 뒤 파생 기획 계약, 구현 계획과 코드를 갱신한다.
4. 기술상 구현 방법만 바뀌고 플레이어 규칙이 같다면 기획 원본은 수정하지 않는다. 개발 저장소의
   구현 계획에 기획 영향이 없는 이유를 기록한다.

기획 규칙이 바뀌었는데 개발 코드만 먼저 확정하거나, 개발 저장소의 파생 문서를 기획 원본처럼
역수정하지 않는다.

## 5. 개발 반입 완료 조건

- 개발 저장소의 원본 매핑표가 이 저장소의 정확한 `main` 커밋을 가리킨다.
- 변경한 모든 원본 문서·절이 하나 이상의 개발 기능에 연결되거나, 아직 반입하지 않은 이유가
  기능 분해표에 기록돼 있다.
- 확정 규칙만 구현 계약으로 사용한다. 가정·미정·검증 필요 항목은 같은 상태를 유지한다.
- 새 공식 용어와 사용하지 않을 표현이 개발 저장소의 용어집에 반영돼 있다.
- 개발 저장소의 기획 계약, 구현 계획과 기능 메타데이터의 revision이 일치한다.

## 6. 충돌 시 기준

- 플레이어 규칙과 용어가 다르면 이 저장소의 최신 `main`을 기준으로 한다.
- 개발 저장소에 아직 반입되지 않은 최신 기획이 있으면 구현을 확정하지 않고 동기화부터 수행한다.
- 기술 제약 때문에 확정 기획을 그대로 구현할 수 없으면 임의로 축소하지 않고 선택지와 영향을
  사용자에게 보고한다.
