# 기획·용어집 담당자 가이드

## 담당 범위

기획 담당자는 다음 두 기준 문서의 품질을 책임집니다.

- `docs/design/<feature-id>.design.md`: 플레이어 경험, 게임 규칙, 밸런스 의도, 수용 조건
- `docs/glossary/GLOSSARY.md`: 기획·UI·코드에서 공통으로 사용하는 공식 용어

구현 파일명, 클래스 구조, 이벤트 연결, 성능 처리 같은 기술 결정은 기획서에 넣지 않고
`docs/implementation/<feature-id>.plan.md`에서 다룹니다.

## 반드시 지킬 규칙

1. 기능은 영구적인 영문 소문자 kebab-case `feature_id` 하나로 식별합니다.
2. 기능 ID, 기존 규칙 ID, 수용 조건 ID는 생성 후 이름을 바꾸거나 재사용하지 않습니다. 더 이상 쓰지
   않는 항목은 삭제 대신 `deprecated`로 표시하고 이유를 남깁니다.
3. 기획서, 구현 계획서, `feature.json`의 `revision`과 `status`는 항상 같아야 합니다.
4. 기획을 변경하면 구현 계획과 코드 영향도 같은 변경에서 반영해야 합니다. 구현된 기능은 기획서만
   먼저 merge할 수 없습니다.
5. 표현만 명확하게 고쳐 실제 규칙과 코드 영향이 없는 경우에도 구현 계획서에 "코드 영향 없음"과 그
   이유를 기록하고 세 산출물의 revision을 함께 올립니다.
6. 기능이나 문서를 삭제하지 않습니다. 폐기할 때는 세 산출물의 status를 `retired`로 바꿔 이력을
   보존합니다.

작업 중인 개인 branch에서는 잠시 불일치할 수 있지만 commit과 PR에는 완결된 세 산출물이 함께 있어야
합니다. 자동 검사와 Git hook이 한쪽만 변경된 commit을 거부합니다.

## 새 기능 기획 절차

1. 기능 ID와 공식 기능명을 정합니다.
2. 아래 명령으로 기획서, 구현 계획서, 코드 manifest를 동시에 만듭니다.

   ```bash
   npm run feature:new -- tower-placement "타워 배치"
   ```

3. 기획서의 목적, 포함·제외 범위, 플레이 흐름을 먼저 작성합니다.
4. 모든 게임 규칙에 `R-001` 형식의 ID를 붙이고 조건, 결과, 예외를 관찰 가능한 문장으로 작성합니다.
5. 모든 완료 기준에 `AC-001` 형식의 ID를 붙입니다. 개발자나 QA가 참·거짓을 판정할 수 있어야 합니다.
6. 새 용어를 용어집에 등록하고 기획서에서 연결합니다.
7. 구현 담당자와 데이터·예외·성능 영향을 검토한 뒤 구현 계획서의 추적표를 채웁니다.
8. 검토가 끝나면 세 산출물의 status를 함께 `planned`로 바꿉니다.

초기 `draft` 상태에는 실제 게임 로직이 없어도 됩니다. 이 경우 코드 폴더에는 추적용 `feature.json`만
둡니다. `planned`부터는 구현 계획서가 기획 규칙과 수용 조건을 빠짐없이 연결해야 합니다.

## 기존 기능 변경 절차

1. 변경 이유와 영향을 받을 규칙 ID·수용 조건 ID를 찾습니다.
2. 기존 항목을 몰래 덮어쓰지 않고 기획서 변경 이력에 새 revision 행을 추가합니다.
3. 세 산출물의 revision을 정확히 1 올립니다.
4. 구현 담당자에게 다음 내용을 전달합니다.
   - 추가·변경·폐기된 규칙 ID
   - 플레이어에게 달라지는 결과
   - 저장 데이터와 기존 플레이 상태에 미칠 가능성
   - 밸런스 수치 변경 범위
   - 새로 추가하거나 의미가 바뀐 용어
5. 구현 계획, 로직, 테스트 반영을 확인한 뒤 같은 commit 또는 PR로 merge합니다.

긴급하게 코드가 먼저 수정된 경우에도 같은 규칙이 반대로 적용됩니다. 기획 담당자는 실제 동작을
확인해 기획 규칙과 수용 조건을 보정하고, 불일치가 남은 상태로 merge하지 않습니다.

## 용어집 작성 규칙

모든 용어에는 아래 정보가 필요합니다.

- 변경하지 않는 영문 `term-id`
- 화면과 기획서에서 사용할 정식 표시명
- 코드에서 사용할 영문 코드명
- 이 프로젝트에서의 정확한 정의
- 혼용하면 안 되는 과거 명칭과 유사어
- 영향을 받는 `feature_id`
- 처음 도입되거나 변경된 기능 revision 또는 ADR 번호

같은 대상에 두 이름을 만들지 않으며, 단수·복수나 번역 차이로 의미가 갈릴 수 있으면 허용 표기를
명시합니다. 용어 의미를 바꾸면 관련 기능 모두의 기획·계획·코드 세트를 함께 검토합니다.

## 기획 문장 품질 기준

- "적당히", "빠르게", "일정 확률" 대신 수치, 계산식 또는 결정 주체를 적습니다.
- 정상 흐름뿐 아니라 입력 불가, 자원 부족, 중복 요청, 일시정지, 재접속 같은 예외를 적습니다.
- 화면 연출과 게임 판정 규칙을 구분합니다.
- 밸런스 숫자는 현재 초기값과 기획 의도를 함께 적어 숫자만 남지 않게 합니다.
- 미래 아이디어는 현재 범위와 섞지 않고 `제외` 또는 `미결정 사항`에 둡니다.

## 전달 전 점검

- [ ] `feature_id`, revision, status가 세 산출물에서 일치함
- [ ] 포함 범위와 제외 범위가 명확함
- [ ] 모든 규칙과 수용 조건에 안정적인 ID가 있음
- [ ] 구현 계획 추적표에서 모든 규칙·수용 조건을 찾을 수 있음
- [ ] 새 용어와 변경 용어가 용어집에 반영됨
- [ ] 변경 이력에 이유와 구현 영향이 기록됨
- [ ] `npm run feature:check`가 통과함

전체 상태와 자동 검사 방식은 [`FEATURE_WORKFLOW.md`](FEATURE_WORKFLOW.md)를 함께 참고합니다.
