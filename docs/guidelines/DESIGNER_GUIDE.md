# 기획·용어집 담당자 가이드

## 담당 범위

기획 담당자는 현재 저장소의 다음 문서를 관리한다.

- `docs/game-design`: 플레이어 경험, 게임 규칙, 콘텐츠와 공식 용어를 기록하는 기획 문서
- `docs/guidelines`: 기획 문서를 작성하고 검토하는 방법을 기록하는 지침 문서

게임 코드의 구조, 내부 데이터 형식, 저장 방식, 성능 처리와 런타임 오류 처리는 사용자가 별도로 요청하고 범위를 합의한 경우에만 다룬다. 존재하지 않는 구현 계획서나 자동 검사 도구가 있다고 가정하지 않는다.

개발 저장소로 기획을 전달할 때는 `DEVELOPMENT_HANDOFF.md`를 함께 따른다. 이 저장소의 기획
담당자는 기능 ID, 규칙 ID와 수용 조건 ID를 만들거나 관리하지 않는다. 해당 ID는 개발 담당자가
기획을 반입하며 부여한다.

## 반드시 지킬 규칙

1. 기획 문서는 내용을 알아볼 수 있는 파일명과 절 제목으로 구분한다.
2. 기획 규칙을 추적하기 위한 기능 ID, 규칙 ID와 수용 조건 ID는 사용하지 않는다.
3. 문서 상단의 상태는 실제 합의 상태와 일치시킨다. 확정하지 않은 내용은 `가정`, `미정` 또는 `검증 필요`로 구분한다.
4. 같은 규칙, 수치와 용어는 하나의 원본에서만 관리한다. 다른 문서에는 내용을 복제하지 않고 원본 문서를 참조한다.
5. 규칙을 변경할 때는 관련 문서, 확인 사례, 공식 용어와 변경 기록에 미치는 영향을 함께 확인한다.
6. 저장소에 실제로 존재하지 않는 문서, 명령, Git hook 또는 자동화 검사가 동작한다고 가정하지 않는다.

## 새 기획 문서 작성 절차

1. 작업 시작 절차에 따라 기존 Markdown 문서를 모두 확인한다.
2. 문서의 목적과 이 문서가 원본으로 소유할 규칙을 밝힌다.
3. 포함 범위와 제외 범위를 구분한다.
4. 필요한 공식 용어가 `docs/game-design/terminology.md`에 있는지 확인한다.
5. 시작 조건, 진행 순서, 플레이어 선택, 제한, 우선순위와 종료 조건을 절별로 작성한다.
6. 정상 상황뿐 아니라 예외 상황과 실패 상황에서 플레이어가 겪는 결과를 작성한다.
7. 개발자와 기획자가 결과를 확인할 수 있도록 상황별 확인 표나 구체적인 예시를 작성한다.
8. 문서 상태, 관련 원본과 변경 기록을 작성한다.

## 기존 기획 변경 절차

1. 변경하려는 규칙의 원본 문서를 먼저 찾는다.
2. 변경이 다른 전투, 카드, 맵, 경제, UI와 용어에 미치는 영향을 확인한다.
3. 원본 규칙을 수정하고, 같은 내용을 가진 중복 문장이 있다면 참조 문장으로 정리한다.
4. 관련 확인 사례와 예시가 새 규칙에 맞는지 갱신한다.
5. 의미가 추가되거나 바뀐 공식 용어를 용어집에 반영한다.
6. 변경 기록에 변경 내용, 이유와 영향 범위를 남긴다.

## 용어집 작성 규칙

용어집은 `docs/game-design/terminology.md`를 원본으로 사용하며 다음 정보를 기록한다.

- 공식 용어
- 쉬운 뜻
- Dino TD에서의 정확한 정의
- 실제 게임 예시
- 사용하지 않을 표현

같은 대상에 여러 이름을 만들지 않는다. 새로운 반복 용어는 다른 기획 문서보다 용어집에 먼저 등록한다. 기존 용어의 의미를 바꾸면 그 용어를 사용하는 모든 기획 문서를 함께 확인한다.

## 기획 문장 품질 기준

- `적당히`, `빠르게`, `일정 확률`처럼 판단 기준이 없는 표현 대신 수치, 계산식 또는 결정 주체를 적는다.
- 아직 수치를 정하지 않았다면 임의로 채우지 않고 `미정` 또는 `검증 필요`로 표시한다.
- 화면 연출과 실제 게임 판정 규칙을 구분한다.
- 밸런스 수치는 현재 기본값과 조정 목적을 함께 적어 숫자만 남지 않게 한다.
- 미래 아이디어는 현재 확정 범위와 섞지 않고 후속 기획이나 미정 사항으로 분리한다.
- 새로운 단어는 `쉬운 한국어 의미 → 실제 게임 예시 → 결정 영향` 순서로 설명한다.

## 전달 전 점검

- [ ] 문서의 목적, 포함 범위와 제외 범위가 분명하다.
- [ ] 확정·가정·미정·검증 필요 상태가 실제 합의와 일치한다.
- [ ] 같은 규칙, 수치와 용어가 여러 문서에서 서로 다른 원본처럼 쓰이지 않는다.
- [ ] 새 용어와 변경된 용어가 공식 용어집에 반영됐다.
- [ ] 정상·예외·실패 상황을 상황별 확인 표나 예시로 확인할 수 있다.
- [ ] 모든 상대경로 참조가 실제 파일로 연결된다.
- [ ] Markdown 파일이 UTF-8로 열리고 병합 표시가 남아 있지 않다.
- [ ] `git diff --check`가 통과하고 변경 파일이 현재 작업 범위를 벗어나지 않는다.

## 개발 인계 점검

- [ ] 변경한 문서와 절, 결정 상태, 변경 이유와 플레이어 영향을 정리했다.
- [ ] 관련 원본·확인 사례·변경 기록·공식 용어를 함께 확인했다.
- [ ] 작업 브랜치가 `main`에 병합됐고 전달할 `main` 커밋을 확인했다.
- [ ] 개발용 기능 ID나 규칙 ID를 이 저장소의 기획 문서에 추가하지 않았다.
- [ ] 구현이나 테스트에서 시작된 기획 변경도 개발 문서보다 이 저장소의 원본에 먼저 반영했다.
